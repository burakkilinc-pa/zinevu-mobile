# The AR terrace measurement — App Clip

A customer in a veranda funnel taps "Weet je je maten niet?", scans a QR code (or
gets the App Clip card on their own phone), and iOS puts **this** on screen with
nothing installed. It measures the terrace with ARKit and writes the size onto
the configurator draft the funnel is already holding. Android measures in the
browser with WebXR instead — Safari has no `immersive-ar` at all, which is the
whole reason this exists.

Both platforms write the **same measurement** to the **same draft**:
`app.veranduo/src/features/configurator-3d/lib/ar/measurement.ts` ⇄
`Measurement.swift`. Nothing downstream — the desktop that resizes the veranda,
the lead, the quote — knows which one measured.

## Identity — must match the website byte for byte

| | |
|---|---|
| Team | `MPM7UW8NS4` |
| Parent app | `com.zinevu.mobile` (this app) |
| App Clip | `com.zinevu.mobile.Clip` |
| Domain | `app.zinevu.com` |
| Invocation URL | `https://app.zinevu.com/ar/{dealer-slug}?id={draft}&lang=nl&from=qr` |

The same identifiers live in `app.veranduo/src/lib/appClip.js`, which builds the
association document at `/.well-known/apple-app-site-association`. Change one
and you must change both — a mismatch shows no card, logs nothing, and Apple's
CDN caches the wrong answer for hours.

**`appclips:` only, never `applinks:`.** An `applinks` claim on `/ar/*` would
mean "somebody with the app installed opens the app instead of the clip", and
this app is the dealer portal — it cannot measure a terrace. It also used to
make the clip untestable: whoever installed the old measuring app had every
scanned QR open that app, so the clip could never be seen on the one device it
was being tested on.

## Running it from Xcode

**An App Clip run from Xcode is handed NO invocation URL.** There is no QR code
in the debugger, so `onContinueUserActivity` never fires, the clip opens with no
draft, and it correctly reports that it cannot find the design — which reads
exactly like a bug and is not one.

`_XCAppClipURL` is Apple's answer. In Xcode: **Product → Scheme → Edit Scheme →
ZinevuMeasureClip → Run → Arguments → Environment Variables**, add

```
_XCAppClipURL = https://app.zinevu.com/ar/{slug}?id={draft-uuid}&lang=nl&from=qr
```

and Xcode launches the clip with a user activity carrying that URL, exactly as a
real scan would — a real draft, a real save, the whole flow without a second
device. Get a draft uuid by opening the configurator, pressing "Weet je je maten
niet?", and copying the `id=` out of the link under the QR code. A stale uuid
measures fine and simply has nothing to save into.

`ios/` is generated by `expo prebuild`, so this scheme edit does not survive a
regeneration. It takes twenty seconds to redo; that is why it is written down
rather than committed.

## Why the card does not appear yet

Safari's App Clip card has one prerequisite no amount of code satisfies: a
version of the parent app **with the App Clip, released on the App Store**
(Apple, *Testing the launch experience of your App Clip*). A Local Experience in
Settings → Developer covers App Clip Codes, QR codes and NFC — not Safari. Until
that release ships, `_XCAppClipURL` above is the way to run this.

Still to do in App Store Connect, on the **Zinevu** app: an **Advanced App Clip
Experience** with URL prefix `https://app.zinevu.com/ar`, plus the card's title,
subtitle and header image.
